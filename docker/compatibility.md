## What the first run found

Four things, none of which a fixture could have told us.

### opencode `1.18.13` writes SQLite, not JSON files

The current release on npm — what anyone installing today gets — keeps its
sessions in `$XDG_DATA_HOME/opencode/opencode.db`. There is no `storage/`
tree at all.

Lantern's opencode adapter read the JSON layout, so at the time **it read
nothing from a current install**. Secondary sources describe the 1.x line as
file-based; that is not what 1.18.13 does.

Since fixed — the database is read directly, and both layouts are supported.
See "What the SQLite run found" below.

### A real Codex `session_meta` line is 21,682 bytes

Larger than the 16 KB window the adapter reads to identify a session, because
Codex embeds the full assembled instructions in it as `base_instructions`.

The growing-window fix was already in — added in response to a review, against a
hand-made 20 KB fixture. This confirms it was not hypothetical: **without it,
every real Codex session would have been invisible**, and the adapter would have
reported an empty history rather than an error.

### Codex opens every session with an injected `user` turn

`<environment_context>` — cwd, shell, sandbox policy. Nobody typed it, but it is
the first user message, and the conversation list uses that as the session
title. Every Codex session was titled with a block of XML.

Fixed, with the block dropped as scaffolding and a fixture added.

### `world_state` is a top-level rollout type not previously seen

It lands in `ignored` rather than `unparsed`, which is the intended behaviour —
but it was not a type any fixture contained, and it is a reminder that the
`ignored`/`unparsed` split is what makes a format change visible.

## What the Qwen Code run found

### Qwen Code is not a Gemini CLI reader, and the plan assumed it was

PR-7 was planned as "one adapter, two ids" on the grounds that Qwen Code is a
Gemini CLI fork writing the same on-disk shape. It does not.

|                   | Qwen Code `0.21.6`                                  | Gemini CLI `0.53.1`                                                                                                                                     |
| ----------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session path      | `~/.qwen/projects/<encoded-cwd>/chats/<uuid>.jsonl` | `~/.gemini/tmp/<slug>/chats/session-<ts>-<id>.jsonl`                                                                                                    |
| Project identity  | cwd encoded into the directory name                 | slug, resolved through `~/.gemini/projects.json`                                                                                                        |
| File semantics    | append-only transcript                              | **replay log** — `{$rewindTo}` deletes a message and everything after it, a repeated `id` overwrites, `{$set:{messages}}` is a checkpoint that rebuilds |
| Envelope          | `uuid`/`parentUuid`/`cwd`/`version` — Claude Code's | `sessionId`/`projectHash` + message records                                                                                                             |
| Working directory | stamped on every record                             | not recorded per message                                                                                                                                |

They need separate adapters. The Gemini CLI column was read from the shipped
`@google/gemini-cli-core@0.53.1` source, not observed on disk — Gemini CLI
cannot be run here, so no adapter is written from it. Shipping one from a
reading of the source is the exact mistake that produced the invented Codex
`session_index.jsonl`.

### Its transcript under-reports its own token use

An assistant record carries `usageMetadata` for the call that produced it — but
a turn that only runs internal tools produces no assistant record at all. In one
of four captured sessions that loses two of three API calls: **2050/129 tokens
reported against a true 6150/884**.

The accurate numbers are in the `system`/`ui_telemetry` records, which Qwen Code
writes for every API call whether or not it produced a message. Summed, they
reproduce the CLI's own per-session roll-up in `usage_record.jsonl` exactly, for
every captured session. The adapter sums those and keeps `usageMetadata` only as
a fallback for an install with telemetry switched off.

Worth noting that the telemetry records are also the ones the adapter refuses to
render — they are instrumentation, not conversation. Counting them as `ignored`
and still mining them for tokens is the useful distinction.

### The project directory is Claude Code's lossy encoding

`/work` becomes `-work`. A directory whose own name contains a dash is
indistinguishable from a separator, so it is never decoded back — the real path
is read from the transcript, where every record stamps `cwd`. Guessing would
file sessions under a workspace they never ran in.

## What the Copilot CLI run found

### BYOK does not need a Copilot subscription

The question that blocked PR-8. It does not: with `COPILOT_PROVIDER_TYPE`,
`COPILOT_PROVIDER_BASE_URL` and `COPILOT_MODEL` set, `1.0.78` starts, answers,
runs tools and writes a full session log against a local Ollama with no GitHub
credential anywhere in the container.

### It writes an event stream, and a SQLite index of the same thing

`session-state/<uuid>/events.jsonl` is the transcript: one typed event per line,
`{type, data, id, timestamp, parentId}`. Beside it sit `session.db` per session
and `session-store.db` at the root — a real schema with `sessions`, `turns`,
`checkpoints`, `assistant_usage_events` and an FTS index.

Only the event log is read. The databases hold a derived view of what the log
already says, and reading SQLite is a different storage mode rather than another
dialect. Worth knowing they exist, though: a future release could invert which
of the two is authoritative, exactly as opencode did.

### The prompt is stored twice, and one copy has scaffolding baked in

`user.message` carries `content` — what the person typed — and
`transformedContent`, the same text wrapped in an injected `<current_datetime>`
block and a `<system_reminder>` listing database tables. Rendering the wrong one
would open every session with a timestamp and make it the title, which is the
mistake Codex's `<environment_context>` already taught once.

`system.message` is the CLI's own system prompt, thousands of words nobody
typed. It is ignored rather than rendered, for the same reason.

### A turn is assembled, not read

The assistant's text and its tool requests arrive together on one
`assistant.message`; each tool's outcome arrives later on its own
`tool.execution_complete`, matched by `toolCallId`. The adapter reserves the
result's place when it sees the call, so the two stay adjacent however far apart
they were logged.

Tokens are reported once, in `session.shutdown`, per model — so a session killed
rather than closed reports none, and usage is optional rather than assumed.

## What the SQLite run found

### opencode's database is the same dialect, in tables

`message` and `part` hold the very JSON the file layout wrote — one document per
row in a `data` column — so the existing parser reads both layouts unchanged.
Only the storage moved. The `session` row is better than the file tree at one
thing: it totals its own `cost` and token counts, so nothing has to be
re-derived from the parts.

This closes the gap the first harness run opened. A current opencode install
went from **reading nothing** to reading every session it has.

### The file layout is still read, and asked first

An install that migrated leaves the old directories behind, and one that never
migrated has no database. Asking the tree first means a half-migrated directory
reads whichever layout actually holds the sessions.

### Opening a foreign database is lazy, and that mislabels a corrupt one

`new DatabaseSync(path, { readOnly: true })` does not look at the file header —
SQLite validates on the first statement. A file that is not a database opens
happily and fails at the first query, where it would have been reported as
`schema-changed`: blaming the CLI for a format change when the file is simply
corrupt or absent. The reader now runs one throwaway query while opening, so
those two cases stay distinguishable.

`immutable` is deliberately not used. It would skip locking entirely, but it
also ignores the write-ahead log — and a running CLI keeps its newest turns
there. A stale history read without complaint is worse than a failure.

### goose runs, and needs its own dialect

goose `1.45.0` drives against Ollama and writes
`sessions/sessions.db`: `sessions(id, name, working_dir)`,
`messages(session_id, role, content_json)`, and a `usage_ledger` per model.

Its `content_json` is goose's own shape — `text`, `thinking`,
`toolRequest{id,toolCall}`, `toolResponse{id,toolResult}` — and nothing like
opencode's parts. So the storage backend is reusable and the parser is not:
goose is a separate adapter, not a second consumer of this one. Recorded here
so that work starts from the schema rather than a description of it.

## When a CLI releases

1. Bump the `ARG *_VERSION` in `cli/Dockerfile.*` to the new exact version.
   Pin it — never `latest`. A floating tag means this table describes something
   other than what ran.
2. `./run.sh`.
3. If a source drops to `supported: false`, or sessions render empty, the format
   moved. Fix the adapter, add a fixture for the new shape, and **keep the old
   fixture**: both versions are in the wild.
4. Update the row above and commit.

The point of pinning is that this table means something. "Works with the latest
version" is not checkable a month later; "works with 2.1.221" is.

## Reading the results

Three things look like bugs and are not:

- **"Sort N new" classifies nothing on the default model.** The classification
  prompt asks for a JSON array covering forty conversations; a 0.6B model
  answers, but not in a parseable shape. Everything up to that point is real —
  the CLI is found, run headlessly, and its structured output parsed correctly.
  Raise `OLLAMA_MODEL` to watch it succeed.

- **Cost shows as unknown for every session.** The harness model is not in any
  price table, so nothing is invented. That is the intended behaviour, and it is
  worth confirming rather than working around.
- **A fixed adapter does not re-parse sessions already in the cache.** Sync is
  gated on file mtime, so an adapter change only affects sessions read after it.
  To re-read everything, drop the state volume:
  `docker compose -f compose.yaml rm -sf lantern && docker volume rm lantern-harness_lantern_state`.
  Real users hit this on upgrade too.
