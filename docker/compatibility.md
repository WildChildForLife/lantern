# CLI compatibility

Which CLI versions Lantern has been **observed** to read — produced by running
that version and reading what it wrote, not inferred from a format description.

Regenerated by running `./run.sh`. Every row is a claim that can be re-checked.

| CLI         | Verified version | Storage observed                                | Lantern reads it | Verified   |
| ----------- | ---------------- | ----------------------------------------------- | ---------------- | ---------- |
| Claude Code | `2.1.258`        | `projects/<slug>/<uuid>.jsonl`                  | ✅               | 2026-09-03 |
| Codex       | `0.152.1`        | `sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl` | ✅               | 2026-09-03 |
| opencode    | `1.18.27`        | `opencode.db` (SQLite)                          | ✅               | 2026-09-03 |
| Qwen Code   | `0.22.3`         | `projects/<encoded-cwd>/chats/<uuid>.jsonl`     | ✅               | 2026-09-03 |
| Copilot CLI | `1.0.82`         | `session-state/<uuid>/events.jsonl`             | ✅               | 2026-09-03 |
| goose       | `1.48.0`         | `sessions/sessions.db` (SQLite)                 | ✅               | 2026-09-03 |

Still read, and re-checked at the same time: Claude Code `2.1.221`, Codex
`0.146.0`, opencode `1.18.13`, Qwen Code `0.21.6`, Copilot CLI `1.0.78`, goose
`1.45.0` — the versions in the row above before the September bump.

That is the half of a version bump nobody watches. A user's history does not
get rewritten when their CLI updates: the sessions on disk this morning were
written by whatever was installed then, and a reader that only handles the
newest release quietly drops all of them.

So the old sessions were kept in the harness volumes rather than discarded,
and every one was parsed again after the bump. **55 sessions across both
generations, every one with zero unparsed lines and — once `AtisLatchEntrySchema`
was added, below — zero parse errors:**

| Source      | old sessions   | new sessions  |
| ----------- | -------------- | ------------- |
| Claude Code | 4 × `2.1.221`  | 1 × `2.1.258` |
| Codex       | 12 × `0.146.0` | 4 × `0.152.1` |
| opencode    | 3 × `1.18.13`  | 4 × `1.18.27` |
| Qwen Code   | 8 × `0.21.6`   | 4 × `0.22.3`  |
| Copilot CLI | 4 × `1.0.78`   | 3 × `1.0.82`  |
| goose       | 4 × `1.45.0`   | 4 × `1.48.0`  |

opencode and goose are the sharper cases of the six, because there both
generations live in _one_ database that the newer CLI migrated in place — the
old rows are read through the new schema, not from an old file left alongside.

Re-checking this is a matter of pointing each adapter's parser at the volumes
and asserting `unparsed == 0` while requiring both generations to be present, so
the check cannot pass by finding nothing. Four of the six stamp the version
inside the session, so the split is read straight off the data; goose stamps
nothing, and its two generations are told apart by run date and by the
`schema_version` row, which went 15 → 16 between them.

The volumes are the regression cover here, which is why step 4 below says to
keep them. `fixtures/` is not: it holds captures from _earlier_ releases
(Claude Code `2.0.28`, Codex `0.141.0`, Qwen Code `0.21.6`), which is worth
having and is read by the unit suite on every run, but it is a different set of
versions from the row above.

Cannot be driven here at all:

| CLI        | Why                                                                     |
| ---------- | ----------------------------------------------------------------------- |
| Gemini CLI | No `base_url` and no OpenAI-compatible auth type, so it cannot be aimed |
|            | at a local model. Its format is also not Qwen Code's — see below.       |

## What the first run found

Four things, none of which a fixture could have told us.

### opencode `1.18.13` writes SQLite, not JSON files

The current release on npm — what anyone installing today gets — keeps its
sessions in `$XDG_DATA_HOME/opencode/opencode.db`. There is no `storage/`
tree at all.

Lantern's opencode adapter read the JSON layout, so at the time **it read
nothing from a current install**. Secondary sources describe the 1.x line as
file-based; that is not what 1.18.13 does.

Since fixed — the database is read directly, and both layouts are supported.
See "What the SQLite run found" below.

### A real Codex `session_meta` line is 21,682 bytes

Larger than the 16 KB window the adapter reads to identify a session, because
Codex embeds the full assembled instructions in it as `base_instructions`.

The growing-window fix was already in — added in response to a review, against a
hand-made 20 KB fixture. This confirms it was not hypothetical: **without it,
every real Codex session would have been invisible**, and the adapter would have
reported an empty history rather than an error.

### Codex opens every session with an injected `user` turn

`<environment_context>` — cwd, shell, sandbox policy. Nobody typed it, but it is
the first user message, and the conversation list uses that as the session
title. Every Codex session was titled with a block of XML.

Fixed, with the block dropped as scaffolding and a fixture added.

### `world_state` is a top-level rollout type not previously seen

It lands in `ignored` rather than `unparsed`, which is the intended behaviour —
but it was not a type any fixture contained, and it is a reminder that the
`ignored`/`unparsed` split is what makes a format change visible.

## What the Qwen Code run found

### Qwen Code is not a Gemini CLI reader, and the plan assumed it was

PR-7 was planned as "one adapter, two ids" on the grounds that Qwen Code is a
Gemini CLI fork writing the same on-disk shape. It does not.

|                   | Qwen Code `0.21.6`                                  | Gemini CLI `0.53.1`                                                                                                                                     |
| ----------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session path      | `~/.qwen/projects/<encoded-cwd>/chats/<uuid>.jsonl` | `~/.gemini/tmp/<slug>/chats/session-<ts>-<id>.jsonl`                                                                                                    |
| Project identity  | cwd encoded into the directory name                 | slug, resolved through `~/.gemini/projects.json`                                                                                                        |
| File semantics    | append-only transcript                              | **replay log** — `{$rewindTo}` deletes a message and everything after it, a repeated `id` overwrites, `{$set:{messages}}` is a checkpoint that rebuilds |
| Envelope          | `uuid`/`parentUuid`/`cwd`/`version` — Claude Code's | `sessionId`/`projectHash` + message records                                                                                                             |
| Working directory | stamped on every record                             | not recorded per message                                                                                                                                |

They need separate adapters. The Gemini CLI column was read from the shipped
`@google/gemini-cli-core@0.53.1` source, not observed on disk — Gemini CLI
cannot be run here, so no adapter is written from it. Shipping one from a
reading of the source is the exact mistake that produced the invented Codex
`session_index.jsonl`.

### Its transcript under-reports its own token use

An assistant record carries `usageMetadata` for the call that produced it — but
a turn that only runs internal tools produces no assistant record at all. In one
of four captured sessions that loses two of three API calls: **2050/129 tokens
reported against a true 6150/884**.

The accurate numbers are in the `system`/`ui_telemetry` records, which Qwen Code
writes for every API call whether or not it produced a message. Summed, they
reproduce the CLI's own per-session roll-up in `usage_record.jsonl` exactly, for
every captured session. The adapter sums those and keeps `usageMetadata` only as
a fallback for an install with telemetry switched off.

Worth noting that the telemetry records are also the ones the adapter refuses to
render — they are instrumentation, not conversation. Counting them as `ignored`
and still mining them for tokens is the useful distinction.

### The project directory is Claude Code's lossy encoding

`/work` becomes `-work`. A directory whose own name contains a dash is
indistinguishable from a separator, so it is never decoded back — the real path
is read from the transcript, where every record stamps `cwd`. Guessing would
file sessions under a workspace they never ran in.

## What the Copilot CLI run found

### BYOK does not need a Copilot subscription

The question that blocked PR-8. It does not: with `COPILOT_PROVIDER_TYPE`,
`COPILOT_PROVIDER_BASE_URL` and `COPILOT_MODEL` set, `1.0.78` starts, answers,
runs tools and writes a full session log against a local Ollama with no GitHub
credential anywhere in the container.

### It writes an event stream, and a SQLite index of the same thing

`session-state/<uuid>/events.jsonl` is the transcript: one typed event per line,
`{type, data, id, timestamp, parentId}`. Beside it sit `session.db` per session
and `session-store.db` at the root — a real schema with `sessions`, `turns`,
`checkpoints`, `assistant_usage_events` and an FTS index.

Only the event log is read. The databases hold a derived view of what the log
already says, and reading SQLite is a different storage mode rather than another
dialect. Worth knowing they exist, though: a future release could invert which
of the two is authoritative, exactly as opencode did.

### The prompt is stored twice, and one copy has scaffolding baked in

`user.message` carries `content` — what the person typed — and
`transformedContent`, the same text wrapped in an injected `<current_datetime>`
block and a `<system_reminder>` listing database tables. Rendering the wrong one
would open every session with a timestamp and make it the title, which is the
mistake Codex's `<environment_context>` already taught once.

`system.message` is the CLI's own system prompt, thousands of words nobody
typed. It is ignored rather than rendered, for the same reason.

### A turn is assembled, not read

The assistant's text and its tool requests arrive together on one
`assistant.message`; each tool's outcome arrives later on its own
`tool.execution_complete`, matched by `toolCallId`. The adapter reserves the
result's place when it sees the call, so the two stay adjacent however far apart
they were logged.

Tokens are reported once, in `session.shutdown`, per model — so a session killed
rather than closed reports none, and usage is optional rather than assumed.

## What the SQLite run found

### opencode's database is the same dialect, in tables

`message` and `part` hold the very JSON the file layout wrote — one document per
row in a `data` column — so the existing parser reads both layouts unchanged.
Only the storage moved. The `session` row is better than the file tree at one
thing: it totals its own `cost` and token counts, so nothing has to be
re-derived from the parts.

This closes the gap the first harness run opened. A current opencode install
went from **reading nothing** to reading every session it has.

### The file layout is still read, but the database is asked first

An install that migrated leaves the old directories behind, so a `storage/` tree
with projects in it is not evidence that the tree is where the sessions are —
on every install that upgraded, it is a leftover. Asking it first would pin
those installs to the history they had on the day they migrated, and report it
as read successfully.

So the database wins whenever it holds any session at all. The tree is read when
there is no database, and when the database has nothing in it yet — which is
what a fresh install that has not run looks like. Whether the database holds
sessions is one `limit 1` query, and the answer is remembered once it is yes,
because a database that has sessions does not stop having them.

### A database that will not open is not an install with no history

The two are opposite problems and only one of them is the user's. `detect`
reports `unreadable` for a file that is not a database, `schema-changed` for one
whose tables have moved, and keeps `no-data` for the install that genuinely has
no sessions yet. Listing fails outright rather than returning nothing, because
an empty listing is how the sync engine is told a source has been emptied — and
it acts on that by deleting the cached rows.

### Opening a foreign database is lazy, and that mislabels a corrupt one

`new DatabaseSync(path, { readOnly: true })` does not look at the file header —
SQLite validates on the first statement. A file that is not a database opens
happily and fails at the first query, where it would have been reported as
`schema-changed`: blaming the CLI for a format change when the file is simply
corrupt or absent. The reader now runs one throwaway query while opening, so
those two cases stay distinguishable.

`immutable` is deliberately not used. It would skip locking entirely, but it
also ignores the write-ahead log — and a running CLI keeps its newest turns
there. A stale history read without complaint is worse than a failure.

### goose runs, and needed its own dialect (now read)

goose `1.45.0` drives against Ollama and writes
`sessions/sessions.db`: `sessions(id, name, working_dir)`,
`messages(session_id, role, content_json)`, and a `usage_ledger` per model.

Its `content_json` is goose's own shape — `text`, `thinking`,
`toolRequest{id,toolCall}`, `toolResponse{id,toolResult}` — and nothing like
opencode's parts. So the storage backend is reusable and the parser is not:
goose is a separate adapter, not a second consumer of this one. Since built —
the backend was reused unchanged, which is the point of having one.

## What the goose run found

### It streams reasoning one token per part

A goose message holds an array of parts, and a streamed turn writes one part
per chunk: `{"type":"thinking","thinking":"Okay"}`, then another for the next
word. Rendered one entry per part, a single conversation in the capture became
**1,486 blocks of roughly a word each**.

Nothing in the schema says this — the parts look like ordinary content until
you count them. A run of the same kind is now joined back into the block it was
before it was streamed, which takes that session to 13 entries. Only real data
shows this; a hand-written fixture would have had one tidy `thinking` part.

### A tool can fail at two levels

`toolResult.status: "error"` is the call never running — goose reports the tool
was not found. But a call with `status: "success"` can still carry
`value.isError: true`, which is the tool running and returning a failure. Both
mean the user did not get what they asked for, and both render as an error.

### Cost is null against a local provider

`accumulated_cost` is null rather than zero, and the adapter keeps that
distinction: a zero would read as a session that was free rather than one that
was never priced. Token counts are recorded and are used.

## What the September 2026 version bump found

Six CLIs moved forward at once. One broke, one changed shape without breaking
anything, and one turned out to keep its whole history somewhere the reader had
to already be handling.

### Claude Code `2.1.258` writes an entry type the schema union rejected

`{"type":"atis-latch","atis":"","sessionId":"…"}`. `ConversationSchema` is a
closed union, so those lines failed to parse and `parseJsonl` returned them as
`x-error` — which the transcript renders, on purpose, because a line Lantern
could not read is the thing a reader most needs to see. The one captured
2.1.258 session held two of them, so it rendered two parse errors; how many a
session carries is not known beyond that.

Nothing was lost — the entry is bookkeeping, and the rest of the file parsed —
but it rendered as damage. `AtisLatchEntrySchema` is now in the union and
classified `internal`, so it is read and never drawn.

Worth being precise about why a fixture could not have caught this: a fixture
only contains entry types its author already knew about. The 2.1.221 capture
from the previous run has no `atis-latch` line anywhere in it.

No fixture was added for it either, which is the standing practice for entries
filed as `internal` — none of `mode`, `last-prompt`, `worktree-state` or
`frame-link` has one, because a fixture asserts what renders and these render
nothing. The cover is in the unit tests instead:
`AtisLatchEntrySchema.test.ts` for the shape, `parseJsonl.test.ts` for the
symptom that was reported, and `conversationRows.test.ts` for the filtering.

### The same release injects companion `user` turns, and those were already handled

`isMeta: true, turnCompanion: true` on a user entry whose content reads
`[Your previous response had no visible output. Please continue and produce a
user-visible response.]`. Nobody typed it, and rendered plainly it would open a
session with scaffolding — the mistake Codex's `<environment_context>` and
Copilot's `transformedContent` each taught once already.

It needed no change: `isMeta` was already on `BaseEntrySchema` and the renderer
already collapses those entries. `turnCompanion` and `apiBlockIndex` are new
fields that nothing reads. Recorded because "we checked and it was fine" is a
result, and the next reader should not have to re-derive it.

### Codex `0.152.1` renamed the events it writes, in the half nothing reads

The `event_msg` stream lost `agent_message`, `agent_reasoning` and
`user_message`, and gained `item_completed` wrapping an item whose own type is
PascalCase — `AgentMessage`, `Reasoning`, `UserMessage`.

The rollout adapter is untouched by this: it reads `response_item` lines and
counts every `event_msg` as ignored. `response_item` still carries `message`,
`reasoning`, `function_call` and `function_call_output` exactly as before, and
all four captured rollouts parse with zero unparsed lines.

The renaming did matter somewhere else, though, and it was worth chasing rather
than assuming: topic naming shells out to `codex exec --json` and picks the
answer out by matching `item.type == "agent_message"`. If the PascalCase names
had reached that stream too, topic naming would have gone on succeeding while
returning an empty answer — a silent failure, not a visible one.

Checked directly against `0.152.1` rather than reasoned about. It has not: the
exec stream still emits `{"type":"item.completed","item":{"type":"agent_message",
"text":"banana"}}`, snake_case, alongside `thread.started`, `turn.started` and a
`turn.completed` carrying usage. Two different vocabularies for the same events
in the same release, in the file and on the wire.

One harness note from doing it: `codex exec` blocks on "Reading additional input
from stdin..." when stdin is neither a TTY nor closed. The entrypoints get a TTY
from `compose run` and never hit it; anything driving Codex non-interactively
needs `< /dev/null`.

### goose `1.48.0` keeps its sessions in the write-ahead log

`sessions.db` is 4 KB. `sessions.db-wal` beside it is 3.4 MB, and every session
from the run is in it — the database file proper has been checkpointed almost
not at all.

This is the case the reader was already built for: `immutable` is deliberately
not used, precisely because it ignores the WAL. Confirmed rather than assumed
now — a reader that opened this file immutably would have reported a goose
install with no history at all, and been wrong about every session in it.

The schema is otherwise unchanged from `1.45.0`. `schema_version` has gained a
row, so a migration did run; it did not touch `sessions`, `messages` or
`usage_ledger`.

### The other three moved without moving

- **opencode `1.18.27`** — still SQLite, no `storage/` tree. Table definitions
  are byte-identical to the `1.18.13` fixture, and the part kinds are the same
  set.
- **Qwen Code `0.22.3`** — same path layout, same record keys, same subtypes.
  The summed `ui_telemetry` records still reproduce its own
  `usage_record.jsonl` roll-up exactly (`6150/906`, `4100/1070`), which is the
  property the adapter depends on for token counts.
- **Copilot CLI `1.0.82`** — same envelope, same event types. BYOK still starts
  and runs with no GitHub credential in the container, so the finding that
  unblocked PR-8 holds a version later. One captured session was killed rather
  than closed and reports no usage, which is the documented behaviour rather
  than a regression.

## When a CLI releases

1. Bump the `ARG *_VERSION` in `cli/Dockerfile.*` **and in `Dockerfile.lantern`**
   to the new exact version. Pin it — never `latest`. A floating tag means this
   table describes something other than what ran. `Dockerfile.lantern` installs
   the same CLIs alongside Lantern for the topic-naming path, and it is the one
   that gets forgotten: the September 2026 bump missed it and left this table
   claiming six versions that image did not install.
2. `./run.sh`.
3. If a source drops to `supported: false`, or sessions render empty, the format
   moved. Fix the adapter, add a fixture for the new shape, and **keep the old
   fixture**: both versions are in the wild. A shape that renders nothing —
   bookkeeping filed as `internal` — takes unit tests instead of a fixture.
4. Re-read the sessions the _previous_ version wrote, which are still in the
   volumes, and check they parse too. A bump that gains the new shape and loses
   the old one looks like a pass from the new sessions alone — and a user
   upgrading has a disk full of the old ones.
5. Update the row above and commit.

The point of pinning is that this table means something. "Works with the latest
version" is not checkable a month later; "works with 2.1.258" is.

## Reading the results

Three things look like bugs and are not:

- **"Sort N new" classifies nothing on the default model.** The classification
  prompt asks for a JSON array covering forty conversations; a 0.6B model
  answers, but not in a parseable shape. Everything up to that point is real —
  the CLI is found, run headlessly, and its structured output parsed correctly.
  Raise `OLLAMA_MODEL` to watch it succeed.

- **Cost shows as unknown for every session.** The harness model is not in any
  price table, so nothing is invented. That is the intended behaviour, and it is
  worth confirming rather than working around.
- **A fixed adapter does not re-parse sessions already in the cache.** Sync is
  gated on file mtime, so an adapter change only affects sessions read after it.
  To re-read everything, drop the state volume:
  `docker compose -f compose.yaml rm -sf lantern && docker volume rm lantern-harness_lantern_state`.
  Real users hit this on upgrade too.
